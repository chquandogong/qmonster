# v1.38 UX Bundle — Metrics Overlay, Wrap Fix, Action Explainer, Toggle Keys

- Status: draft (pending operator review)
- Author session date: 2026-05-04
- Target version (mission ledger): `v1.38.0`
- Bundle scope: four operator-facing UI improvements, all backwards-compatible

## 1. Why this bundle

The operator surfaced four UX gaps while running v1.37.0:

1. **No at-a-glance metrics view.** `CTX`, `QUOTA 5H`, `QUOTA 7D`, `MEM`, `RESET`, `TOKENS`, `COST` are scattered across each pane card; comparing pressure across multiple panes requires scrolling and reading text. The eye cannot tell _bounded_ (cap is real, e.g. percentages, reset windows) from _unbounded_ (no cap, e.g. cumulative tokens or cost) without reading the unit.
2. **Pane card text truncates when narrow.** `path:`, `cmd:`, `status:`, severity reason, and recommendation `effect`/`lever`/`detail` lines use `aligned_field()` and are rendered through `ratatui::List`, which does not wrap. Existing wrap is only applied to badge rows via `wrap_badge_line()`. On a narrow split or small terminal, value content drops off the right edge with no continuation.
3. **`p` / `d` / `y` actions are opaque.** The keys execute immediately and emit a SystemNotice _after the fact_ — operators do not know in advance what will be sent, what will be rejected, or what will land in the clipboard, nor why each action is recommended. This conflicts with the project's observe-first principle (`PROJECT_BRIEF.md §28-31`).
4. **Overlay close UX is inconsistent.** Help (`?`) toggles on the entry key, but Settings (`S`), Provider Setup (`P`), and Target picker (`t`) close only on `q` / `Esc`. New overlays added by this bundle inherit the inconsistency unless we lock in a contract.

This bundle ships a single coordinated v1.38.0 release covering all four. None of the changes alter audit semantics, policy gates, or the `SignalSet` schema — they are pure UI/UX layered on existing data.

## 2. Goals / Non-goals

**Goals**

- Provide a dedicated **Metrics Overlay** that distinguishes bounded from unbounded values visually and supports per-pane comparison plus selected-pane time-series detail.
- Make every pane card line wrap with a continuation indent that aligns under its value column, so no information is silently dropped.
- Replace the silent-execute behavior of `p` / `d` / `y` with a **review-then-confirm** flow (default), while letting power users opt out.
- Standardize overlay UX: **every** overlay (existing + new) renders an `[x]` close glyph and toggles on its entry key; existing close keys (`q`, `Esc`) keep working.
- Document what changed in v1.37.0 in operator-facing terms (this lives in the conversation summary, not in this spec — see §10 for the canonical `UI_MANUAL.md` snippet).

**Non-goals**

- No change to provider adapters, audit chain, policy gates, or `SignalSet` schema.
- No changes to mission/contract documents beyond a v1.38.0 ledger sync.
- No write paths to provider config files (Provider Setup remains read-only).
- No new persistence — Metrics Overlay reads existing in-memory `PaneReport`s and existing SQLite `recent_token_samples`.
- No multi-window aggregation in the Metrics Overlay; it scopes to the current target's panes only (matches Alerts/Panes scoping).

### 3.1 Overlay-state contract

All overlays share a small contract:

| Property                      | Value                                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Entry key                     | character key (e.g. `m`, `S`, `P`, `t`, `?`)                                                                                                            |
| Close keys                    | `Esc`, `q`, **the entry key again**, click `[x]`                                                                                                        |
| Body close button             | rendered top-right via `close_button_rect()` (existing helper)                                                                                          |
| Modal-while-editing exception | Settings: when a numeric edit is in flight, `Esc` cancels the edit (not the overlay), `q` is consumed as a typed digit (already implemented; preserved) |

The toggle-on-entry-key behavior is implemented at the `tui_loop.rs` dispatch layer — when the key matches an overlay's entry key and that overlay is currently open, dispatch `close()` instead of `open()`. This avoids modifying every overlay's per-overlay key handler.

### 3.2 Visual language

| Source class                                                                | Visual                                                                                                                  | Cap shown?                                          |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Ratio in [0..1] (`context_pressure`, `quota_*_pressure`, `cache_hit_ratio`) | Horizontal progress bar `█████░░░░░ 56%` with severity color (SAFE/CONCERN/WARNING/RISK) and tick marks at 60 / 75 / 85 | Yes — bar has a hard right edge                     |
| Reset ETA (`quota_*_resets_at`)                                             | Inverse-progress bar showing window-elapsed-fraction + textual ETA `2h13m`                                              | Yes — measured against the window length (5h or 7d) |
| Cumulative count / currency / RSS                                           | Sparkline (8-block Unicode) + current value + Δ vs prior sample                                                         | No — line shape conveys trend                       |
| Static fact (no historical samples, no cap, e.g. `MEM-FILE`)                | Current value + trend arrow against last poll                                                                           | No                                                  |

The sparkline-vs-bar split is itself the bounded/unbounded signal.

## 4. Feature 1: Metrics Overlay (`m`)

### 4.1 Activation and dismissal

- Entry key: **`m`** (currently free across all dispatchers — verified).
- Close: `m` again, `Esc`, `q`, click `[x]` top-right of the modal.
- Mouse wheel scrolls the body **only when rendered content height exceeds modal body height**; otherwise wheel events are ignored. Computed at render time from the rendered line count vs `metrics_modal_rects.body.height`.
- `↑` / `↓` / `j` / `k`: select pane in the comparison table (drives the bottom selected-pane detail section). Selection clamps to `[0, reports.len() - 1]`; no wrap-around.

### 4.2 Layout

Modal occupies 88% width × 80% height of the viewport, centered. Layout is two stacked sections inside one `Block`:

### 4.3 Section A — Hottest banner

Computed at render time from the in-scope `&[PaneReport]`. The "hottest pane" is the pane with the largest single bounded pressure value across `context_pressure`, `quota_5h_pressure`, `quota_weekly_pressure`. If all panes have no bounded pressure data, the banner reads `Hottest: —` and is dimmed.

### 4.4 Section B — Comparison table (bounded only)

One row per pane in the current target. Columns are fixed: `CTX | 5H | 7D | CACHE | COST` — a deliberate mix of one bounded ratio that is universally interesting, plus the two split-quota windows, plus a cache hit signal, plus a tiny cost peek (rendered as a number, not a bar — cost is unbounded but we want the comparison row to show _something_ about each pane on a single line).

- **Bars**: 6 cells wide. Filled chars show severity color (`severity_color()` from `ui::theme`, same scale as pane card badges). Tick marks at 60% / 75% / 85% are rendered as a thin vertical guide on the unfilled side.
- **Missing data**: an em-dash `─` plus dim style. We never synthesize a value (S3-4 honesty rule).
- **Selection cursor**: `▶ ` prefix on the active row; mirrors the panes-list cursor convention.

### 4.5 Section C — Selected-pane detail (mixed bounded + unbounded)

Driven by the row selected in Section B. Shows:

- **TOKENS in / out sparklines**: pulled from `recent_token_samples` (existing `crate::store::TokenSample`). Twin lines, oldest-to-newest left-to-right, 8-block Unicode glyphs. Current absolute value and `Δ` vs prior sample on the right.
- **COST sparkline**: cumulative `cost_usd` from the same samples (when present). Renders absolute current value `$N.NN`; trend arrow `▲ / ─ / ▼` indicates whether the most recent delta is positive, zero, or negative (only positive deltas are expected).
- **MEM RSS / MEM-FILE**: current value + delta vs last polled value (no sparkline today; no historical store). Trend arrow only.
- **5H reset / 7D reset**: textual ETA + a window-elapsed bar (`(window_secs − eta_secs) / window_secs`). Window sizes: `WINDOW_5H_SECS = 5 * 3600`, `WINDOW_7D_SECS = 7 * 86400`. Falls back to dim em-dash when `quota_*_resets_at` is `None`.
- **Source badges line**: `sources [Official] [Heur]` summarizing which `SourceKind`s contributed to the visible badges, mirroring the pane-card honesty convention.

## 5. Feature 2: Pane card text wrap fix

### 5.1 Affected lines

Lines currently produced by `aligned_field()` and rendered through `ratatui::List` (no wrap):

- `path  : <value>` (`pane_list_lines_with_flash`)
- `cmd   : <value>` (same)
- `status: <value>` (same)
- `state : <value>` (`render_pane_state_row_with_flash`)
- `<severity_label> : <reason>` (per-recommendation in expanded card)
- `effect: ...`, `lever: ...`, `detail: ...` (from `expanded_detail_field()`)

### 5.2 Approach

Add a small helper in `panels.rs`:

```rust
fn wrap_aligned_field(
    label: &str,
    value: &str,
    wrap_width: u16,
) -> Vec<Line<'static>>;
```

Behavior:

- Computes label column width as `max(8, label.len())`. (Existing `aligned_field` uses 8; we keep that as the floor.)
- Continuation indent is `label_col + 2` spaces (matching the `: ` separator), so wrapped chunks line up under the value column.
- Splits the value on grapheme/char boundaries (`unicode-segmentation` is already a transitive dep via ratatui; if not, fall back to `chars().count()` since pane content is ASCII-heavy).
- Returns 1 `Line` when the formatted width fits in `wrap_width`, otherwise N lines with continuation indent.
- When `wrap_width` is below `label_col + 4` (degenerate narrow viewport), returns the single line uncut so the operator at least sees the label and clipping is the renderer's responsibility — this avoids producing zero-character continuation rows.

Replace direct `Line::from(aligned_field(...))` constructions in `pane_list_lines_with_flash`, `render_pane_state_row_with_flash`, and `expanded_detail_field` consumers with `wrap_aligned_field(...)` and `lines.extend(...)`.

### 5.3 Edge cases

- Path ellipsizing already happens upstream (`display_path` caps at 80 chars). Wrapping is a second layer in case the wrap_width is even narrower than the ellipsis budget.
- `aligned_field` is called inside `expanded_detail_field`, which is then re-wrapped by callers in `recommendation_detail_lines`. The wrap helper is idempotent for already-fitting values, so introducing wrapping at the inner call is safe.
- Mouse hit-testing for pane selection: `pane_index_at_row` already counts lines via `pane_list_lines_with_width` and consumes its caller's `wrap_width`. Adding more lines to `pane_list_lines_with_width` must propagate through that helper _automatically_ because it iterates the returned `Vec<Line>` length — no additional change needed. **Test**: `pane_index_at_row_handles_wrapped_path_line()`.

### 5.4 Tests (Wrap fix)

- `wrap_aligned_field_no_wrap_when_value_fits()` — value short enough returns one line.
- `wrap_aligned_field_continuation_indent_matches_label_col()` — wrapped continuation begins with `label_col + 2` spaces.
- `wrap_aligned_field_handles_narrow_width_gracefully()` — wrap_width below floor returns one line uncut.
- `pane_card_path_line_wraps_when_narrow()` — pane card with a long worktree path under a narrow `wrap_width` produces ≥ 2 lines, second line is indented.
- `pane_index_at_row_handles_wrapped_path_line()` — hit-testing still maps mouse rows to the right pane after wrapping increases the card's line count.

## 6. Feature 3: Action explainer for `p` / `d` / `y`

### 6.1 What changes

Each of `p`, `d`, `y` is intercepted before the existing handler runs. By default the keystroke opens an **Action Explainer** modal that previews the action, its rationale, and its audit chain. Pressing `Enter` confirms; `Esc`, `q`, the same key again, or `[x]` cancels.

Power-users can opt out via `[ux] confirm_actions = "never"` in `qmonster.toml` to restore the v1.37.0 immediate-execute behavior.

In addition, an inline preview line is **always** rendered:

- On the selected pane card (when a pending prompt-send proposal exists): `proposal: /compact  → press p to accept · d to reject` — gives the operator a 1-line summary without needing to open the modal.
- On the selected alert (when it carries `suggested_command`): `copy: /clear  → press y to copy` — same visual treatment.

The inline preview is observe-first: it doesn't require pressing any key to learn what the action is.

### 6.2 Config

```toml
# ~/.qmonster/config/qmonster.toml
[ux]
# How often to show the action-explainer modal before executing p / d / y.
# - "always":     show every time (safest; default)
# - "first_time": show once per action kind per session, then execute directly
# - "never":      never show; restore v1.37.0 immediate-execute behavior
confirm_actions = "always"
```

Default: `"always"`. The reasoning: we are introducing a confirmation step on previously-immediate keys. Defaulting to `"always"` is the conservative choice; an operator who finds it noisy can switch to `"first_time"` or `"never"` once they have read the modal once. `"first_time"` state is _session-local_ — restarting Qmonster re-arms the prompt — so we never persist whether-the-operator-has-seen-it across runs.

### 6.3 Modal content

```
┌ Action: Accept prompt-send proposal · Enter confirm · Esc cancel  [x]┐
│                                                                       │
│ Target pane    : codex:1:review · %57                                 │
│ What to send   : /compact                                             │
│ Why now        : cache: drift detected — /compact will let cache      │
│                  rebuild (cache 64% → 30%, 6 samples) [Qmonster]      │
│ Severity       : CONCERN  source [Qmonster]                           │
│ Audit chain    : Execute → PromptSendAccepted → PromptSendCompleted   │
│ Mode now       : observe_only  ⚠  prompt sends are blocked            │
│                                                                       │
│ Press Enter to confirm · Esc / p again / click [x] to cancel          │
└───────────────────────────────────────────────────────────────────────┘
```

Field rules:

- **Target pane** — `session:window · provider role · pane_id` (matches pane card title).
- **What to send / What to reject / What to copy** — depends on the action.
- **Why now** — pulled from the underlying `Recommendation::reason` (proposal source) or `SystemNotice` (alert source); always carries its `[SourceKind]`.
- **Severity** — when applicable.
- **Audit chain** — pre-computed for the current `actions.mode`:
  - `p` Execute mode: `Execute → PromptSendAccepted → PromptSendCompleted` _or_ `... → PromptSendFailed`.
  - `p` AutoSendOff: `AutoSendOff → PromptSendAccepted + PromptSendBlocked`.
  - `p` observe_only: `observe_only → PromptSendBlocked`.
  - `d`: `PromptSendRejected`.
  - `y`: `(no audit event — clipboard write only)`.
- **Mode warning** — surfaced when the configured mode means the apparent action is partially or fully blocked (observe_only `p`, `allow_auto_prompt_send=false`).

### 6.4 Modal kinds

```rust
// src/app/action_explainer.rs
pub enum PendingAction {
    // pane_idx is the index into the dashboard's reports slice;
    // mirrors how dashboard.pane_state.selected() is used today.
    AcceptPromptSend { pane_idx: usize },
    RejectPromptSend { pane_idx: usize },
    // alert_idx is the index into the visible-alerts slice the
    // existing AlertCommandCopyView builds; same index space as
    // dashboard.alert_state.selected().
    CopyAlertCommand { alert_idx: usize },
}

pub struct ActionExplainModal {
    pending: Option<PendingAction>,
    // pre-computed view shared with renderer
    view: Option<ActionExplainView>,
    // session-local "first_time" memory — set true on first confirmed
    // execute of each kind; checked when [ux] confirm_actions = "first_time"
    seen_accept: bool,
    seen_reject: bool,
    seen_copy: bool,
}

pub struct ActionExplainView {
    title: String,             // e.g. "Accept prompt-send proposal"
    target_label: String,      // e.g. "codex:1:review · %57"
    payload_label: String,     // "What to send" / "What to reject" / "What to copy"
    payload_text: String,      // e.g. "/compact"
    why: String,
    why_source: SourceKind,
    severity: Option<Severity>,
    audit_chain: String,
    mode_warning: Option<String>,

```

The modal does not re-derive what the action is; it stores `PendingAction` and on `Enter` calls the existing handlers (`handle_prompt_send_action`, `copy_selected_alert_command_to_clipboard`) with the same arguments the keystroke would have passed in v1.37.0. This keeps the audit-chain authoritative path unchanged.

The proposal payload (`payload_text` for `AcceptPromptSend` / `RejectPromptSend`) is sourced from the existing `first_prompt_send_proposal(&PaneReport)` helper in `prompt_send_actions.rs`, which filters `report.effects` for `RequestedEffect::PromptSendProposed { slash_command, .. }`. There is no new field on `PaneReport`.

### 6.5 Inline preview rendering

In `panels.rs::pane_list_lines_with_flash`, when the pane carries a `RequestedEffect::PromptSendProposed { slash_command, .. }` in `report.effects` (detected via the existing `first_prompt_send_proposal` helper, made `pub(crate)` so `panels.rs` can reuse it), insert a `proposal:` line above the recommendation block in the expanded card. The line content is `<slash_command>  → press p to accept · d to reject`. Wrapped via the new `wrap_aligned_field` helper (Feature 2). Inserted only on the **expanded (selected) pane card** — not on every pane — to mirror the `p`/`d` keys' actual scope.

In `alerts.rs::render_alerts`, on the **currently selected alert only** (driven by `alert_state.selected()`), when its `suggested_command` is `Some(cmd)`, append `copy: <cmd> → press y to copy` as a dim line below the existing detail rows. The line uses the existing alert detail pathway and respects the same wrap behavior as other alert detail lines. When the selected alert has no `suggested_command`, no inline `copy:` line is rendered (matches the "nothing to copy" SystemNotice path in `copy_selected_alert_command_to_clipboard`).

## 7. Feature 4: Toggle keys and `[x]` consistency

### 7.1 Behavior contract

| Overlay                                   | Entry key      | Toggle on entry key? Today | Toggle on entry key? After v1.38 |
| ----------------------------------------- | -------------- | -------------------------- | -------------------------------- |
| Help (`?`)                                | `?`            | ✅ yes                     | ✅ yes (no change)               |
| Settings (`S`)                            | `S`            | ❌                         | ✅ yes                           |
| Provider Setup (`P`)                      | `P`            | ❌                         | ✅ yes                           |
| Target picker (`t`)                       | `t`            | ❌                         | ✅ yes                           |
| Metrics (`m`, NEW)                        | `m`            | n/a                        | ✅ yes                           |
| Action explainer (intercepts `p`/`d`/`y`) | the action key | n/a                        | ✅ yes — second press cancels    |
| Git (mouse-only entry)                    | —              | n/a (no entry key)         | n/a                              |

### 7.2 Implementation

In `tui_loop.rs` there is one `Event::Key` arm per overlay-already-open branch (`if git_modal.is_open() { ... continue; }`, etc.). Today these branches forward all keys to the per-overlay handler. After v1.38:

```rust
if settings_overlay.is_open() {
    if k.code == KeyCode::Char('S') && !settings_overlay.is_editing() {
        settings_overlay.close();
        continue;
    }
    // existing handler...
}
```

The Settings exception (`!is_editing()`) preserves the in-place numeric edit mode where `S` would otherwise be typed as a digit — though `S` is not a digit, the same gate is applied for symmetry with the existing `q` rule.

For Target picker, the analogous gate: `if target_picker.open && k.code == KeyCode::Char('t') { close_picker(); continue; }`.

For the Action explainer modal, the gate checks the originating key (`'p'` for AcceptPromptSend, `'d'` for RejectPromptSend, `'y'` for CopyAlertCommand): pressing the same key while the modal is open closes it without executing.

### 7.3 `[x]` close button

All four existing overlays already render `[x]` via the shared `close_button_rect()` in `dashboard.rs` (verified in code: Help line 289, Provider Setup line 448, Settings via `settings_close_button_rect`). The two new overlays (Metrics, Action explainer) inherit this — both call `close_button_rect()` in their renderers.

Target picker today does **not** render `[x]`. We add it; the existing mouse handler already has a `close_picker()` path, we just need a click-region check.

## 9. Risks and open questions

### 9.1 Risks

- **Modal noise on busy panes.** With `confirm_actions = "always"` (default), an operator who has been firing `p`/`d` rapidly in v1.37.0 will need an extra `Enter`. Mitigated by `"first_time"` and `"never"` settings; documented in `UI_MANUAL.md`.
- **Wrap fix changes pane card heights.** Pane index hit-testing relies on counting `Vec<Line>` length; we assert this in tests but bears watching in case other consumers (mouse drag for split divider) take stale row counts.
- **Metrics Overlay competes with Alerts/Panes for screen space.** Modal is overlaid (Clear widget), so does not push the dashboard. No conflict.

### 9.2 Open questions

- **Reset window size for non-Claude/Codex providers.** We use `5 * 3600` and `7 * 86400` literals. Gemini's reset cadence is documented at `Pro` / `Flash` family granularity (per F-4b) but the **window** size for the bar isn't a Gemini concept; we still render reset eta as a textual string and skip the bar for non-window providers. Acceptable for v1.38; revisit if a future Gemini source surfaces window-bounded quotas.
- **`MEM-FILE` time series.** Today `agent_memory_bytes` is polled but not stored in `recent_token_samples`. We render only current value + trend arrow against the previous poll. Persistent time-series for `MEM-FILE` would require a new SQLite column; explicitly out of scope for v1.38.
- **Inline preview for `p` and `d` collision.** A pane may have a pending proposal AND be the target of a recommendation that is _not_ yet a proposal. The inline `proposal:` line shows the proposal; recommendations remain as today. No conflict, but the operator needs to know the difference — covered by an addition to `UI_MANUAL.md §3`.
