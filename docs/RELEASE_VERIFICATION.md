# Release Verification

Each tagged release of Qmonster ships with multiple independent ways to
verify what you downloaded. The GitHub release body repeats the short
commands for that tag; this page keeps the longer explanation and scope
notes.

## 1. Checksums

`checksums.txt` (SHA-256) is included in every release and covers all
other release assets. After downloading, run:

```sh
sha256sum -c checksums.txt
```

## 2. Build provenance attestation

Release assets are signed by a GitHub Actions workflow run via
[`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance).
Verify with the GitHub CLI:

```sh
gh attestation verify qmonster-vX.Y.Z-linux-x86_64.tar.gz \
  --repo chquandogong/qmonster
```

The same command works against the npm tarball
(`qmonster-X.Y.Z.tgz`), the SBOM, and `checksums.txt`. A passing run
proves the asset was produced by this repository's release workflow at
the matching tag.

## 3. SBOM attestation

The Linux binary tarball also has an independent SBOM attestation
generated with GitHub's `actions/attest` SBOM mode. Verify it with the
SPDX predicate type:

```sh
gh attestation verify qmonster-vX.Y.Z-linux-x86_64.tar.gz \
  --repo chquandogong/qmonster \
  --predicate-type https://spdx.dev/Document/v2.3
```

This proves the SBOM predicate was signed by this repository's release
workflow for the binary tarball.

## 4. SBOM (SPDX-JSON)

Each release includes `qmonster-vX.Y.Z-sbom.spdx.json` — a Software Bill
of Materials in SPDX-JSON format generated by
[`anchore/sbom-action`](https://github.com/anchore/sbom-action) at
release time. The action scans the unpacked release binary directory
(`qmonster-vX.Y.Z-linux-x86_64/`) which contains the compiled `qmonster`
binary plus the bundled `README.md`, `LICENSE`, `VERSION.md`,
`qmonster.example.toml`, and `Cargo.lock`. The lockfile is shipped with
the release so syft's `rust-cargo-lock` cataloger can extract the full
dependency graph and so downstream operators can audit the deps
independently. Inspect the resolved dependency set without running the
binary:

```sh
jq '.packages[] | {name, versionInfo, licenseConcluded}' \
  qmonster-vX.Y.Z-sbom.spdx.json
```

Scope and limits:

- The SBOM reflects the contents of the binary tarball you downloaded.
  It does not currently extend to the npm source tarball
  (`qmonster-X.Y.Z.tgz`) or to transitive build-time toolchain
  packages outside the released artifact.
- The SBOM file itself is also covered by the build provenance
  attestation, and the binary tarball has the independent SBOM
  attestation described above. Verifying both gives downstream
  operators confidence that the dependency graph was emitted by this
  repository's release workflow at the matching tag and bound to the
  released binary tarball.

## 5. SBOM diff summary

Each release also includes `sbom-diff-summary.txt`. The release workflow
downloads the previous semver release SBOM when available, compares the
package set, and fails if the current SBOM package count drops below the
larger of 50 packages or half of the previous release count. This catches
cataloger regressions like the v1.36.2 one-package SBOM collapse while
still allowing normal dependency churn.
