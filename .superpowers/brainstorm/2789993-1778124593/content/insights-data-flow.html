Token Insight Data Flow

The first slice should reuse existing SQLite tables, then add one focused lifecycle table for outcomes that cannot be inferred honestly.

observe -> classify -> recommend -> outcome -> insight
Existing Sources

token_usage_samples

input/output/cached/cost time series per pane.

audit_events

RecommendationEmitted, AlertFired, ArchiveWritten, SnapshotWritten, PromptSend*.

cost_usage_events

Positive USD deltas and budget thresholds.

New Small Table

recommendation_events

Stable key for pane/action/source/threshold snapshot at emission time.

recommendation_outcomes

accepted, rejected, blocked, archived, snapshot_written, hidden, ignored.

TTL rule

No related outcome within TTL means ignored.

Insights

Situation frequency

Which of the six situations happens most.

Action effectiveness

Which recommendations become real action.

Cache timing

Whether compact was avoided while hot or accepted when cold.

Lifecycle States
emitted -> visible -> accepted / rejected / blocked / ignored

Prompt sends use existing PromptSend audit chains. Snapshot/archive outcomes use existing SnapshotWritten and ArchiveWritten events. Hidden/dismissed should be captured as a lightweight outcome, not guessed from UI state.

Honesty Rule

Do not invent token savings. Show measured deltas and label estimates separately.

Use observed outcome for action counts and TTL ignored only when no correlated action exists.
