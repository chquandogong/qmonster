Token Optimization Insight Surface

Choose the product shape for showing what Qmonster observed, recommended, acted on, or ignored.

A

Extend Metrics Overlay

Add more rows to the existing m overlay: six situations, cache state, latest recommendation, and last action.

Pros

  • Smallest change
  • Uses the current pane-card mental model
  • Good for live monitoring

Cons

  • Weak for history and insight
  • Easy to overcrowd the metrics screen
  • Ignored actions remain hard to explain
B

New Insights Overlay

Add an i overlay focused on token optimization: Situation Matrix, Timeline, Action Ledger, and Cache/Cost panes.

Pros

  • Best fit for operational insight
  • Separates metrics from decisions
  • Can show acted / ignored / blocked clearly

Cons

  • Needs a small recommendation lifecycle ledger
  • More UI surface to maintain
  • Requires clear retention and aggregation rules
C

Report First

Add qmonster insights --since ... and later wire the same data into TUI once the reports are useful.

Pros

  • Fast to validate with real SQLite data
  • Good for demos and review artifacts
  • Low risk to the live TUI

Cons

  • Less compelling during live operation
  • Does not satisfy "open a new screen" as directly
  • May split attention between CLI and TUI
Recommended Direction: B, with a Report-First Slice
Insights Overlay Tabs
Overview: six situations + cache state + savings pressure
Timeline: signal -> recommendation -> operator action -> outcome
Ledger: acted, blocked, dismissed, ignored, auto-snapshot
Evidence: SourceKind, thresholds, docs/code references
First Slice

Use existing SQLite tables to prove value quickly, then add a small lifecycle table only where inference is not enough.

Result: live operator insight plus a credible demo/report path.
